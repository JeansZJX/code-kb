# 团队代码知识库

把项目规则与可核验的代码记录放在团队工作副本中。技能负责读取、查询和维护，不携带某个项目的业务规则，也不假定成员使用相同的绝对路径。

## 定位项目

先遵守当前任务适用的 `AGENTS.md`。从任务目录向上查找 `code-kb.project.json`，用它的 `knowledge_base` 相对项目根定位知识库；没有入口时查找项目的 `.code-kb/manifest.json`，或使用用户明确指定的 `--kb`。技能安装目录不是业务项目根。

读取 manifest 后确认 `project_id`、任务模块、代码源编号、代码源状态与规则文件。正常检出按 `project_relative_root` 定位，切换盘符或检出根目录不应改变共享记录。非标准路径映射放在本机配置；有关配置或初始化问题，读取 [configuration.md](references/configuration.md)。

未初始化的项目可以准备配置与规范框架。现有文件必须保留；业务代码源未接入或仍为 `planned` 时，明确缺口，不编造符号记录。

## 首次整理已有代码

用户要求接入已有代码或索引尚未建立时，在确认代码源后运行内置 `import`，读取配置范围内的实际源码。它使用 Tree-sitter AST 与 Repomix 的语言 grammar 生成候选，保留已有人工整理记录；所需依赖和安装命令见 [configuration.md](references/configuration.md)。

```text
node <技能目录>/scripts/kb.mjs import --project-root <项目根> --module <模块>
```

先核对输出的语言支持、扫描范围和未覆盖文件。再阅读常用公共入口的源码，确认定义、职责、签名和实际引用，把已核验部分写入正式记录。自动导入不改变 accepted 规则或能力推荐；AST 定义候选和文本引用候选不能直接当作完整语义调用图。需要精确引用时，优先使用已配置的语言服务或 IDE 工具。

自动生成代码默认只整理类型与来源，避免重复序列化方法占满知识库；需要生成成员时按配置选择完整导入，或查询原文件。生成代码的修改方式与协议来源仍按项目规则处理。

## 开发前

1. 读取公共规则及任务模块规则，保留状态。`accepted` 是团队已确认规则；`documented` 是有来源但尚待确认的约束；`proposed` 是提案；`superseded` 或项目已有的废弃状态保留迁移信息。结合用户指令和实际代码解决冲突，记录决策依据，不静默改写已确认规则。
2. 查能力目录和当前代码源的符号记录，按目录、命名空间或关键字定位，只读取任务相关记录，避免把整库载入上下文。再用代码搜索核对已有类、函数、公共入口及调用处。文件索引有覆盖范围，搜不到记录不能证明没有实现。
3. 先判断能否复用或扩展。确需新增时，沿用已确认的命名、目录、引用和职责边界。若目录中存在两个类似入口，核对用途与兼容限制后再选，不为了统一而顺带重构无关代码。
4. 核对证据与当前文件。指纹不匹配、文件移位或引用不明时，先读取代码并修正受影响的记录。未核实的记录不能成为实现依据。

可用内置脚本获取状态或文件清单：

```text
node <技能目录>/scripts/kb.mjs status --project-root <项目根>
node <技能目录>/scripts/kb.mjs verify --project-root <项目根> --module <模块>
node <技能目录>/scripts/kb.mjs inventory --project-root <项目根> --module <模块>
```

优先只读查询。不要为了取最新规范自动更新成员的 SVN 工作副本；有本地改动时尤其应保留现场，由用户按团队流程处理同步。

## 开发后

更新本次涉及的代码事实：新增、删除或移动的定义，签名变化，已核实的引用位置，复用入口及其限制。记录使用当前 `project_id`、模块和 `source_id`，所有代码路径相对已登记代码源。标明文件指纹和行证据；按 [record-format.md](references/record-format.md) 保存并验证。

```text
node <技能目录>/scripts/kb.mjs verify --project-root <项目根>
```

只验证影响范围仍应报告范围。未完成的语义解析、未覆盖调用者、未知 SVN 状态要如实保留。文件清单与文本引用证据不等于完整的编译器符号图；重载、反射、生成代码、Unity 序列化绑定等需要额外工具或人工核对。

以下变更可以随开发自动维护：已核验的定义、引用、指纹、废弃和迁移事实，以及能力目录里的真实签名与代码位置。推荐入口的使用语义、限制和替代关系发生变化时，保留原有判断并写入提案。新业务规范、跨模块职责、协议语义、统一命名规则及已确认规则的改变，也保留为提案或已有状态。团队决策有明确依据后再调整状态与适用范围；兼容旧知识库时保留其已有状态名，不自动改名。

## 多模块与分支

客户端、服务端按 manifest 分开登记。每条主干、临时主干、分支保留独立代码源编号和索引位置；不能复用一个编号指向另一分支。新增源或激活正式主干时登记新源，重新核验索引再调整 `active_source`。

分支可以引用公共规范，分支代码事实仍属于该分支。合并之后，从目标主干重新检查定义与引用；不要复制旧指纹把分支记录冒充主干记录。服务端尚未提交时继续维护已提供文档的来源与状态，等待源码后补充代码事实。

## 交付

简述遵守的关键规则、复用或新增的入口、更新的知识记录及验证范围。规则冲突、证据过期或代码源缺失影响结果时说明具体影响。

知识记录应与相关代码一起接受差异检查。除非用户已授权，不提交 SVN、不改 SVN 属性、不发布项目知识到外部仓库。通用技能的升级与项目规则的更新分别维护。
