# 团队代码知识库

让团队知道已有功能在哪里、怎样调用、有哪些约束。覆盖前后端开发、技术策划的脚本与配置工具、技术美术的编辑器工具、Shader 和资源处理流程。知识记录保存在项目中，技能包只包含通用说明。

这是 Markdown 技能，不依赖 Node.js、npm 或其他技能。使用当前环境的文件读取、代码搜索和项目验证工具即可。

技能提供读取规范、查找已有实现和维护必要知识的流程。项目里的网络、事件或业务模块都是知识条目，不是技能的内置功能。条目区分通用机制的调用知识与业务模块知识；团队明确要求遵守的约定才是规范，不把现有实现自动当成标准。

## 定位与记录

遵守适用的 `AGENTS.md`。从任务目录向上查找 `code-kb.project.json`，以其所在目录为项目根，按 `knowledge_base` 定位知识库；路径相对项目根，成员的盘符和检出目录可以不同。缺少入口时使用用户明确指定的位置，不把技能安装目录当成项目根。

读取知识库 `README.md` 的来源表，确认本次来源 ID、代码或文档根、可读状态、适用规范和维护者。未接入的来源只保留缺口，不能据文档猜测代码入口。主干与分支用不同来源 ID，代码事实分别记录。

知识库只维护三类内容：

- `rules/`：团队已确认的稳定规范与必要约束。
- `features/<来源ID>/<功能ID>.md`：有必要积累的知识条目，以短卡记录通用机制或业务模块的入口、调用线索和限制。
- `changes/<日期>-<任务>-<UUID>.md`：一个任务一份独立变更单，保留这次修改的事实与原因。

不维护需要人人改写的总索引、全库版本号或共享 CHANGELOG。按目录和关键字搜索。建立记录、汇总或处理并发时读取 [records.md](references/records.md) 的模板与约定；已有知识库保留原内容，按需要逐步迁移。

## 开发前

由成员先同步任务相关的 SVN 代码和知识库。未同步时说明实际依据的范围，不宣称掌握仓库最新状态；技能不自动更新有本地改动的工作副本。

读取相关规范，搜索当前来源的功能卡，以及提到这些功能 ID、入口或路径的变更单，再核对当前源码。卡片可能尚未汇总，不能只读卡片忽略后续变更；新旧记录互相矛盾时回到代码核验，不能按日期直接覆盖判断。未找到记录时继续搜索源码，避免把“库里没有”当成“项目没有”。

确定复用或扩展入口后再实现，沿用已确认的命名、职责、目录和调用约束。确需新增功能时说明现有入口不适用的原因，不顺带重构无关代码。引用记录只是已核验的实例和检索线索；涉及反射、Unity 序列化绑定、事件、配置驱动或生成代码时，核对任务相关的实际绑定。

公共接口有并行修改或契约分歧时先协调。签名、协议或配置键变化后检索实际受影响的调用及绑定，修正它们并说明未覆盖范围，不能只检查卡片列出的实例。

## 开发后

检查本次代码实际入口、关键调用与适用规则，执行项目需要的编译、测试或资源验证。功能新增、修改或删除，或入口、调用、行为约束、重要决策变化时，写一份新的独立变更单，注明原因、已检查与未检查项。只改注释排版且没有契约或行为变化时，不生成知识记录，保留正常 SVN 提交说明即可。

默认不修改别人维护的功能卡。维护者根据变更单和当前源码汇总相关卡片；本次已获维护者授权时可同步更新卡片，并在变更单中注明。没有明确维护者或汇总授权时保留变更单，交付时说明待汇总事项，不能静默重写共享卡片。每个后续任务新增自己的单据，不续写上一任务的文件。

汇总时在卡片关联本次采用的变更单，不复制历史流水。确需拆开提交代码与单据时，记录实际已发生的对应提交或说明待配对状态；纠正历史判断的新单据指向原记录。

功能卡只保留职责、当前入口和必要调用方式、关键已核验实例或检索线索、必要依赖约束、状态与维护者；废弃入口留下迁移位置。不要抄录全部私有函数、完整源码、重复接口说明或每函数历史。调用线索按影响保留，不能为了固定条数漏掉关键绑定。

不要求每个业务模块都建卡。存在跨模块复用、需共享的接口或容易误用的重要约束时，才单独积累条目；局部实现留在源码中。业务条目仅在相关任务中读取，接入未确认的实现保留缺口，不能当作推荐入口。正式 API 手册已有清楚说明时优先引用，不再抄一份。

新规范或已确认规范的变更先写独立规则提案，由维护者确认；新实现不能自动成为团队规范。代码事实以实际源码为准，规范的状态与决策依据另行保留。

## 整理已有代码

由负责人初始化或授权整理，按业务范围从常用公共入口开始阅读。先查现有卡片与变更单，再核验职责、签名、关键调用与限制，建立能指导复用的短卡。尚未读到或没有验证的内容说明范围，不全库导出定义候选，不宣称形成完整调用图。

## 多人协作与交付

优先各自检出工作副本。多人使用同一个物理目录时，只读可以并行，写入先划分互不重叠的代码和文档范围；同一脚本的修改要协调或隔离。独立变更单减少共享文件编辑，不能保证代码脚本零冲突。

提交前由成员再次同步，重读期间变化的相关规范、卡片、变更单与代码，合并后重新核验。冲突保留双方有效增量，回到源码确认；不能整文件采用最后写入者的版本。在同一 SVN 仓库时，相关代码和变更单尽量同次提交。历史由变更单与 SVN 日志追溯，不填写尚未发生的修订号，不追加每函数历史或文件哈希。

交付简述复用或新增的入口、记录位置、检查范围及待汇总项。技能不提供自动并发锁或假定存在检查器；路径、入口、规则链接、重复功能与关键调用由本次实际检索核验。未经用户授权不提交 SVN，不将项目知识发布到技能分发仓库。
