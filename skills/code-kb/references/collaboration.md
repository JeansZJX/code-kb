# 多人维护知识库

用于多人在 SVN 工作副本中开发、准备提交或处理知识库冲突。这里约定协作步骤；当前工具不会自动同步 SVN、协调成员提交或阻止并发写入。

## 两种冲突

同一版本化文件已被另一成员修改时，未更新的提交会被 SVN 拒绝并提示 `out of date`，成员需要更新并处理合并。若两人修改的是不同文件，后一份提交仍可能成功，即使它依据了旧规范、旧接口或旧代码记录。SVN 的文本合并也可能保留两份互相矛盾的知识。

例如，成员甲修改公共接口和对应记录，成员乙只改一个调用者，两个提交可以不产生文本冲突，但调用者仍可能沿用旧签名。是否兼容需要重新读代码和验证。SVN 的更新与合并机制见 [SVN Book](https://svnbook.red-bean.com/en/1.8/svn.basic.in-action.html)；过期提交说明见 [Apache Subversion FAQ](https://subversion.apache.org/faq.html#out-of-date)。

## 开工与提交

1. 成员开工前更新任务涉及的代码、知识库和项目指令，确认模块、`source_id` 与分支。技能仅查询 SVN 身份和状态；更新工作副本由成员执行，已有授权时按授权范围处理。
2. 在现有任务说明或独立提案中记录本次读取的规则版本、代码基线与范围。可采用独立文件名，例如 `proposals/task-example.md`。SVN 工作副本可能混合修订，不能把根目录修订号当作所有文件的版本；记录实际查到的值，查询不到就保留未知。
3. 开发后只更新受影响的人工记录，保留本次增量和核验范围。新规则写独立提案，不把实现自动变成 `accepted` 标准。
4. 提交前成员再次更新相关代码和知识库，处理文本及语义差异，重读期间改变的规则。更新之后重新检查受影响的实现、指纹、行证据和引用，再执行必要的构建、测试及 `verify`。
5. 同一 SVN 仓库内，将相关代码和知识记录放入同次提交，审查实际提交文件列表，避免只提交新知识而遗漏代码。若两者分属不同仓库，任务记录保留对应提交编号，明确尚未配对的状态。

基线记录用于追溯，不是提交锁。不要为每个任务递增共享的“全库版本号”，这会增加所有成员争抢同一文件的机会。工具当前没有提交基线检查器，流程是否执行仍由成员和团队审查确认。

## 减少共享文件竞争

人工符号记录按模块、代码源和业务职责拆分，例如 `code/app/main/account.json` 与 `code/app/main/resources.json`；同一职责的常用符号可留在一个文件，不必为每个函数建立单独记录。路径和内容遵守 [record-format.md](record-format.md)。

`manifest.json`、`code/index.json`、能力目录和已确认规则由团队约定的维护者审查调整。新增记录仍需登记索引，不能为了避开冲突让记录失去入口。规则提案使用独立文件；是否接受以及迁移范围由团队确认。

全量导入由指定维护者执行，其他成员日常维护任务涉及的已核验记录。当前 `import` 重扫所选模块和代码源的整个配置范围，没有 `--changed` 或 `--file` 模式。它会更新文件清单及中心索引，SVN 修订或本地改动元数据的变化也可能使未改源码的候选文件产生差异。多个模块仍可能共用 `code/index.json`，应错开导入，提交前审查差异。

同一工作副本不要并行执行 `import`、`inventory` 或其他知识库写入。当前工具没有进程锁或事务；中途失败可能留下已写入的部分结果，应检查差异后重跑或恢复受影响的自动输出，保留人工改动。不为每次功能开发重建整个知识库。

## 处理已有冲突

人工记录或规则出现冲突时，先保留双方增量与任务依据，再按合并后的代码逐项确认定义、职责、签名和引用。共享人工记录不使用 `mine-full` 或 `theirs-full` 整文件覆盖作为默认解法，这会丢失另一方的有效修改。确认过时的条目保留迁移或废弃说明。

自动候选、文件清单和索引冲突时，先合并相关源码、人工记录及索引登记，清除 JSON 中的冲突标记。可以重建的纯候选文件可暂保留一份可解析版本，再由一名维护者对对应模块和代码源重新执行 `import`，检查索引登记及导入覆盖范围。已核验或非导入器维护的记录会保留，仍需人工重新核验，不能认为重新导入已经解决全部冲突。

`verify` 能检查登记位置的文件指纹、行号与证据，不能证明工作副本已同步、接口语义相容或全部调用者都已覆盖。SVN 锁、属性和仓库钩子可按实际需要另行设计；本技能不会自动配置这些机制。
