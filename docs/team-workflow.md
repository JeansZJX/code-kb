# 团队操作流程

项目规范和真实代码记录跟随 SVN，通用技能从 GitHub 安装。这样每个成员能在自己的检出目录中使用同一份规则，不需要统一盘符。

## 负责人首次接入

选定技能版本，按 [README](../README.md) 安装并初始化知识库。核对模块与代码源路径，特别是临时主干、正式主干和功能分支；它们应各有稳定编号。初始化模板里的规则是框架，团队需要补充适用范围与已有决策，不能把模板直接标成已确认。

建议先登记团队常用且容易重复实现的入口，如网络收发、事件、配置读取、缓存、资源加载、数据访问、日志、错误处理。对每个入口写清职责、调用方式、限制和真实代码位置；无需一次为所有私有函数补文档。知识库的成本应优先花在复用和变更影响较大的地方。

已有项目先运行 `import` 读取当前源码，取得 AST 定义与文本引用候选，再让 Codex 核对这些常用入口。负责人做一次初始整理，成员按本次开发的影响继续更新；不要让每个成员各写一份完整初始索引。导入保留人工记录，自动候选不等于团队标准。

指定公共规范和各模块规则的负责人。新增规则提交提案，说明要解决的问题、已有实现、迁移成本和适用代码源。负责人依据团队决策确认后，登记状态和决策依据。已有项目文档先保留 `documented`，阅读源码及决策后再确认。

将知识库、入口文件和项目 `AGENTS.md` 约定纳入 SVN。将 `workspace.local.json` 排除提交，个人绝对路径不得写入 manifest、符号记录或能力目录。技能本身可随 SVN 分发，也可各自安装，但应统一版本。

## 成员开始一次开发

在现有 SVN 流程中先检查本地改动，再更新需要的代码和知识库；冲突先处理，Codex 不会自动覆盖工作副本。首次使用可以在请求中明确写：

```text
使用 $code-kb 完成这个功能。先读取已确认规则，查询能复用的类和函数；完成后更新受影响的定义、调用位置和文件指纹，并说明验证范围。
```

配置好项目指令之后，普通代码请求也应触发同样流程。建议先让 Codex 说明本次模块与代码源，尤其是在分支或多份工作副本并存时。源编号与当前任务不符，应先修正选择。

Codex 在开发前查询规则与已有入口，必要时用 `rg`、IDE、LSP 或语言工具核对真实代码。开发后，Codex 随本次改动更新定义和引用证据，运行知识验证以及有关编译、测试。只有文件指纹通过不能证明行为正确；团队仍按既有验收方法检查功能。

成员查看代码与知识库差异，把相关变更放进同一次小提交。文件清单、公共规范和跨模块目录容易产生冲突；按模块和代码源分文件，并避免为小功能重写整库。

## 分支与主干切换

为分支配置单独的源编号、项目相对路径和索引位置。分支沿用公共规范，但可以保留有依据的分支提案。即使两个分支中的类名相同，它们的文件指纹与引用也不能混用。

合并代码后，从目标主干重新核对记录。将分支能力加入公共能力目录前，检查目标代码存在、调用方式有效，以及是否和已有入口重叠。

启用新的正式主干时，新增或激活对应代码源，重新生成清单、登记所需符号并验证，然后调整 `active_source`。保留旧源编号用于追踪；不能只把原编号的路径改到新主干。

## 规则如何改变

| 变更 | Codex 的处理 | 团队的处理 |
| --- | --- | --- |
| 函数签名、文件移动、引用增减 | 核对源码后更新事实记录 | 随代码审查 |
| 新增可复用入口 | 登记代码事实及使用限制 | 决定是否推荐全队使用 |
| 新命名规范、依赖边界、协议语义 | 写入提案，保留已有规则状态 | 确认适用范围与迁移方案 |
| 已确认规则需要例外 | 记录冲突、需求依据和影响 | 明确例外或修改规则 |
| 文档与源码不一致 | 保留两种来源，标明差异 | 确定当前依据并补文档 |

当规则影响正在进行的任务时，先按用户提供的决策推进，并把依据写清。技能不能把偶然采用的写法自动升级为团队标准。

## 升级技能

维护者在测试工作副本中验证新版本，并记录选择的 tag 或 commit SHA。成员用同一版本更新技能；本地安装器的 `--replace` 覆盖包内同名文件，保留其他文件，升级后检查遗留文件。

安装器不会更新 SVN、修改项目规则或迁移已有索引。升级后用 `status` 和 `verify` 确认知识库能读取；需要格式迁移时先查看变更说明，再在保留原文件的前提下执行。

本机路径映射、源码、内部协议和真实索引不应随技能更新发布到公共仓库。
